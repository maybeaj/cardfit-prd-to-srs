# Development Guidelines

## 작업 단위

**태스크 1건 = 이슈 1건 = 파일 1개**(`docs/tasks/<ID>.md`). 태스크 59건이 이슈 `#1~#59`로 발급돼 있다.

## 착수 조건 (Definition of Ready)

- [ ] `Depends on` 이 전건 완료됐다
- [ ] References 문서를 읽었다 — 계산은 CALC, 픽스처는 FXT
- [ ] AC의 판정 기준값이 **명세에서 온 것**이다
- [ ] `mode:fixture` 태스크라면 External Blocker 재개 조건을 이해했다

## 완료 조건 (공통 DoD)

```
□ 모든 Acceptance Criteria를 충족하는가?
□ 대응 테스트 케이스(STD)가 구현되고 통과하는가?
□ 배포 게이트 ①·②를 통과하는가?                    (C-TEC-007a)
□ 의존성 경계 린트를 통과하는가?                     (ADR-02 · IN-04)
□ 픽스처 모드에서 외부 호출 0회로 동작하는가?
□ Linter 경고가 없는가?
□ python3 tools/verify_docs.py 가 통과하는가?
□ 문서 갱신이 필요한 변경이면 해당 명세를 함께 고쳤는가?
```

계산 도메인 4건(BE-06~08 · BE-10)에는 한 항목이 더 붙는다 — **참조 계산기 대조**(`tools/fixtures/expected-results.json`).

## 테스트

- **AC를 새로 만들지 않는다.** STD에 판정 SLO 27건이 있다. 그 수치를 그대로 단언문으로 옮긴다
- 시나리오는 **최소 2개, 그중 1개는 실패 흐름**
- `skip`·`only` 로 남은 테스트는 완료로 보지 않는다
- 시각 의존 테스트는 **데모 클럭을 주입**한다

## 버전 관리

- 커밋 메시지는 `type: 제목 — 부제` + 본문에 ①②③ 구조. 최근 커밋을 참고한다
- 원자적 커밋. 한 커밋이 한 가지를 한다
- 기본 브랜치에 직접 커밋하지 않는다 — 브랜치를 따고 병합한다

## 문서와 코드의 관계

**문서가 앞서고 코드가 그것을 인용한다.** 값이 어긋나면 코드가 아니라 문서를 먼저 본다.

| 값 | 정본 |
| --- | --- |
| 계산 순서 · 전환비용 · 임계값 · 증감 폭 | `[계산 명세서]` |
| 판정 SLO | `[테스트 명세서]` |
| API 스키마 · 에러 코드 · DDL | `[SRS 문서]` §6 |
| 시연 데이터 · 픽스처 경계 | `[픽스처 데이터 명세]` |
| 일정 · 의존성 | `[개발 실행 총괄]` |

**명세를 고쳐야 할 이유를 발견하면 코드로 우회하지 않는다.** 명세를 고치고 `rule_spec_version` 을 올린 뒤 경계값 260건을 재바인딩한다.
