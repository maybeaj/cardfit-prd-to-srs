# 기술 제약 가드레일

## 언제 쓰는가

- 새 npm 패키지를 추가하려 할 때
- "여기는 Redis를 쓰면 빠른데" 같은 판단이 들 때
- 서버 코드를 어디에 놓을지 정할 때
- 배포·스케줄링·CI 설정을 건드릴 때

## 왜 있는가

**C-TEC-001~007은 SRS 1.5가 확정한 제약이다.** 기술적으로 더 나은 대안이 있어도 조용히 우회하면 안 된다. 우회는 발견이 늦고, 발견 시점에는 이미 되돌리기 비싸다.

제약이 요구사항을 깨뜨리는 경우는 실제로 있다 — SRS 1.5.2가 요구사항 27건 중 11건이 이 스택에서 그대로 구현되지 않는다고 기록했고, 1.5.3이 결정 3건을 남겼다. **새 충돌을 찾으면 거기에 적고 논의한다. 코드로 몰래 해결하지 않는다.**

## 체크리스트 — 새 의존성·구성요소

아래에 걸리면 멈춘다.

## 배포 게이트는 1개다

**C-TEC-007a가 허용한 예외는 딱 하나다.**

```
Git Push → ① 경계값 회귀 260건 → ② 금지어 정적 스캔 → 배포
```

빌드·린트·타입검사는 게이트가 아니라 **로컬 `npm run verify`** 에서 잡는다. 게이트를 늘리자는 요구가 오면 SRS 1.5를 먼저 고쳐야 한다.

**모델 식별자만 바꾼 배포에도 게이트 ②가 걸려야 한다** — 코드 변경이 없어 스캔 없이 나갈 수 있다(SRS 1.5.1 신규제약 ④).

## 제약이 막고 있는 것을 발견하면

1. **우회하지 않는다**
2. SRS 1.5.2·1.5.3의 형식으로 **무엇이 왜 막히는지** 적는다
3. 대안 후보와 각각이 어떤 제약을 완화해야 하는지 함께 제시한다
4. 사람이 결정한다
