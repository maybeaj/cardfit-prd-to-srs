CardFit 서비스의 **PRD 문서를 SRS 문서로 변환**하는 작업 저장소입니다.

**변환 완료** — `ai-place-prd-v1_0.md` → `ai-place-srs-v1_0.md`

| 단계 | 상태 |
| --- | --- |

## 1. 작업 목표

`ai-place-prd-v1_0.md`(CardFit PRD)를 SRS 문서로 변환합니다.

**변환의 기준은 표준 원문이 아니라 예시 SRS 문서입니다.**

- ✅ 목표: `[SRS 문서] AD-Core-Platform (한글).md`와 **같은 포맷**의 문서를 만든다
- ❌ 목표가 아님: ISO/IEC/IEEE 29148:2018을 전부 충족하는 풀 버전 SRS를 만든다

즉 예시 SRS의 절 구성·표 구조·ID 체계를 그대로 따르는 것이 1차 원칙입니다.

### 1-1. 예시 SRS 범위를 벗어나는 내용의 처리

PRD에는 예시 SRS가 담지 않는 내용이 있습니다(KPI·Guardrail, 검증 실험 설계, 근거 등급, 리스크·가정·의존성 등). 이런 내용은 다음 규칙으로 다룹니다.

| 상황 | 처리 |
| --- | --- |
| 예시 SRS에 대응 절이 있다 | 예시 포맷에 맞춰 그대로 옮긴다 |
| 예시 SRS에 대응 절이 없다 | **ISO/IEC/IEEE 29148:2018 구성에 따라 해당 부분만 절을 확장해 작성한다** |
| PRD에 없는 정보다 | 임의로 만들지 않고 `TBD`로 표기한다 |

**"해당 부분만"이 핵심입니다.** 확장은 PRD에 실재하는 내용을 담기 위한 최소 범위로 한정하며, 표준을 채우기 위한 빈 절은 만들지 않습니다.

## 2. 파일 구성

| 파일 | 역할 |
| --- | --- |
| `ai-place-prd-v1_0.md` | **입력물** — CardFit PRD 겸 요구사항 추적표 (PRD-CARDFIT-001 v1.0) |
| `ai-place-srs-v1_0.md` | **산출물** — 변환된 SRS (SRS-CARDFIT-001 v1.0) |
| `[SRS 문서] AD-Core-Platform (한글).md` | **포맷 기준** — 광고 플랫폼 SRS. 목표 문서의 형식 견본 |
| `29148-2018-ISOIECIEEE.pdf` | **준거 표준** — 예시 SRS 범위를 벗어난 부분을 확장할 때만 참조 |
| `README.md` | 이 문서 |

> **표준 원문은 이 저장소에 포함되지 않습니다.** ISO/IEC/IEEE 29148:2018은 유료로 판매되는 저작물이라 `.gitignore`로 제외했습니다. 작업 시에는 프로젝트 루트에 직접 두고 참조하세요.

## 3. 포맷 기준 — 예시 SRS의 구성

```
1. 서론          — 목적 · 범위 · 정의/약어
2. 이해관계자     — 역할 · 담당 · 책임
3. 시스템 맥락 및 인터페이스 — 클라이언트 · 내부 서비스 · 외부 시스템
4. 구체적 요구사항
   4.1 기능 요구사항   REQ-FUNC-xxx
   4.2 비기능 요구사항 REQ-NF-xxx
5. 추적성 매트릭스 — 요구사항 ↔ 모듈 ↔ 구현 클래스 ↔ 테스트 케이스
6. 부록          — API 엔드포인트 · 데이터 모델 · 비즈니스 규칙 · DB 스키마
7. 향후 개선 사항
```

요구사항 표의 9개 열:

`ID` · `제목` · `출처` · `우선순위` · `유형` · `검증 방식` · `인수 기준` · `상태` · `담당자`

## 4. PRD → SRS 매핑

### 4-1. 예시 SRS 포맷에 그대로 들어가는 것

| PRD | → | SRS |
| --- | :---: | --- |
| 1절 목적·범위, In/Out 스코프 | → | 1. 서론 |
| 6-4 운영 역할 | → | 2. 이해관계자 |
| 6-2 외부 연동 | → | 3. 시스템 맥락 및 인터페이스 |
| 3절 기능 요구사항 F-01~F-14 (MoSCoW) | → | 4.1 기능 요구사항 `REQ-FUNC-xxx` |
| 4절 비기능 요구사항 | → | 4.2 비기능 요구사항 `REQ-NF-xxx` |
| 5절 Acceptance Criteria | → | 4.1·4.2 표의 **인수 기준** 열 |
| 9절 요구사항 추적표 | → | 5. 추적성 매트릭스 |
| 6-1 핵심 엔터티 / 6-2 API / 6-3 상태 전이 | → | 6. 부록 (데이터 모델 · API · 비즈니스 규칙) |
| 3절 Won't v1 (F-10 · F-14) | → | 7. 향후 개선 사항 |

### 4-2. 예시 SRS 범위를 벗어나 확장한 것 — 실제 결과

| PRD | → SRS | 근거 조항 |
| --- | --- | --- |
| 2절 사용자 시나리오 | **8장** 사용자 특성 및 사용 시나리오 | 9.6.6 User characteristics |
| 10-1 ADR | **9장** 설계 결정 기록 (ADR) | 9.6.16 Design constraints · 9.6.20 Supporting information |
| 10-2·10-3·10-4 리스크·가정·의존성 | **10장** 가정 및 의존성 (10.4 제약 사항 포함) | 9.6.8 Assumptions and dependencies · 9.6.7 Limitations |
| 7절 KPI·Guardrail · 8절 검증 설계 | **11장** 검증 | 9.6.19 Verification |
| 11절 재설정 규칙 | **12장** 재설정 규칙 | 9.6.20 Supporting information |
| 5-2 실패 경로 AC | **4.3** 예외·실패 처리 요구사항 `REQ-EXC-xxx` | 9.6.12 c) 이상 상황 처리 |
| 3-1 스프린트 분할 | **4.1** 요구사항 배분 및 증분 | 9.6.9 Apportioning of requirements |
| 6-3 상태 전이 | **6.5** 상태 전이 규칙 | 9.6.12 b) exact sequence of operations |
| 4절 감사·데이터 운영 | **6.6** 논리 데이터베이스 요구사항 | 9.6.15 Logical database requirements |

**근거 등급 표기(⚪ 🟡 🟠)는 제거했다.** 결정 문장에 붙은 미확인 경고가 결정의 힘을 훼손하므로, 불확실성은 11장 검증과 12장 재설정 규칙으로 위치를 옮겼다. 출처가 확인된 사실을 뜻하는 🔵만 근거 인용으로 유지한다.

### 4-3. PRD에 없어 `TBD`로 남는 것

예시 SRS는 채우고 있으나 CardFit PRD에는 근거가 없는 항목입니다.

- **구현 클래스** (5장) — 모듈 설계가 아직 없다. 모듈 열만 3장의 내부 구성요소로 채웠다
- **물리 스키마** (6.4) — 컬럼 타입·인덱스·파티셔닝 전략
- **클라이언트 플랫폼** (3장) — PRD에 웹/모바일 구분과 진입 도메인이 없다
- **요구사항 단위 개인 담당자** (2·4장) — 역할까지만 기재
- **감사 보존기간**(REQ-NF-006) · **단위원가 상한**(REQ-NF-005) — 의존성 D9·D3에 걸려 있다
- **미결 의존성 D1~D5** — 특히 두 건은 인수 기준을 정량화할 수 없어 `TBD`
  - `D2` Net Benefit 임계값 → REQ-FUNC-004(b) 게이팅 판정 기준
  - `D5` 시나리오 증감 폭 → REQ-FUNC-003(b) 계산 기준

## 5. 원칙

1. **포맷은 예시 SRS를 따른다.** 표준 원문은 확장이 필요한 부분에서만 참조한다.
2. **확장은 최소 범위로 한다.** PRD에 실재하는 내용을 담기 위해서만 절을 늘린다.
3. **없는 내용을 만들지 않는다.** 미정 사항은 `TBD`로 남기고 무엇이 막혀 있는지 함께 적는다.
4. **PRD의 판단을 보존한다.** Net Benefit 게이팅, 스코프 경계(실행 대행 제외), Guardrail 0건 기준은 설계 의도이므로 변환 과정에서 희석하지 않는다.
