## 0. 이 가이드의 사용법

SRS는 **요약을 읽어서 이해되는 문서가 아니다.** 표 45개가 서로를 참조하고 있어서, 한 표만 봐서는 왜 그렇게 정했는지 알 수 없다.

이 가이드는 요약본이 아니라 **읽는 순서와 방법**이다. 아래 세 경로 중 하나를 고른다.

| 경로 | 시간 | 읽을 곳 | 도달점 |
| :---: | :---: | --- | --- |
| **A. 훑기** | 30분 | 이 가이드 1~3장만 | "이 서비스가 뭘 하는지" 설명할 수 있다 |
| **B. 이해** | 2시간 | 가이드 전체 + SRS 5장 순서대로 | "왜 이렇게 설계했는지" 설명할 수 있다 |
| **C. 작업** | 반나절 | B + 담당 영역 정독 + 7장 자가진단 | 요구사항을 근거로 판단을 내릴 수 있다 |

**어느 경로든 3장(이상해 보이는 4가지)은 건너뛰지 않는다.** 이 서비스의 설계는 상식과 어긋나는 지점이 몇 개 있고, 거기서 막히면 나머지가 다 이상해 보인다.

## 1. 한 문장으로

> **카드를 여러 장 가진 사람에게, 앞으로 쓸 돈을 기준으로 어떤 카드를 남기고 없앨지 계산해주는 서비스.**
> **그리고 바꿀 만한 가치가 없으면 "그대로 두세요"라고 정직하게 말한다.**

뒷 문장이 이 제품의 전부다. 앞 문장만 하는 서비스는 이미 여럿 있다.

## 2. 먼저 알아야 할 개념 5개

카드 혜택 용어를 모르면 SRS 4장부터 막힌다. **문구점 도장판**으로 바꿔 보면 전부 익숙한 개념이다.

### 2.1 도장판 비유

| 도장판 | 카드 용어 | SRS 어디 |
| --- | --- | :---: |
| "한 달에 3만원 이상 사면 도장 찍어줌" | **실적구간** | 4.1 REQ-FUNC-003 |
| "할인은 최대 5천원까지만" | **통합할인한도** | 6.2 |
| "도장판 만드는 데 1년에 1만원" | **연회비** | 6.2 |
| "과자는 도장 안 찍어줌" | **제외항목** | 6.4.2 |
| "도장판을 5개 갖고 있는데 뭐가 이득이지?" | **조합 최적화** | 4.1 REQ-FUNC-004 |

### 2.2 이 서비스만의 개념 3개

**① Net Benefit (순혜택)**

```
Gross Benefit  (바꿨을 때 받을 혜택)
    −  전환비용 3항목
       ① 연회비 변동
       ② 실적 재달성 부담   ← 새 카드로 실적을 다시 쌓아야 하는 수고
       ③ 전환 실행 부담      ← 해지·발급하는 데 드는 품
    ─────────────────────
    =  Net Benefit          ← 이 숫자로 판단한다
```

**② 게이팅 (Gating)**

Net Benefit이 **기준선에 못 미치면** 앱이 이렇게 답한다.

> **"지금 그대로 쓰세요."**

이게 이 서비스의 핵심이다. SRS 9장 `ADR-01`이 그 결정 기록이다.

**③ 시나리오 3개**

앞으로 쓸 돈은 아무도 정확히 모른다. 그래서 **적게 · 예상대로 · 많이** 세 가지를 **미리 다 계산해 둔다.** 화면은 "예상대로"로 열리고, 나머지는 탭으로 본다.

## 3. 이상해 보이는 4가지 — 여기가 핵심이다

SRS를 읽다 보면 *"왜 이렇게 불편하게 만들었지?"* 싶은 곳이 나온다. 전부 의도된 것이고, **각각 9장 ADR에 이유가 적혀 있다.**

### 3.1 "그대로 두세요"라고 답하는 게 정상이다

**이상한 점** — 사용자는 뭔가 바뀌길 기대하고 들어왔는데, 앱이 아무것도 바꾸지 말라고 한다.

**이유** — 바꾸는 데 드는 비용(전환비용 3항목)이 얻는 혜택보다 크면, 바꾸라고 권하는 건 **사용자에게 손해를 끼치는 것**이다.

**어디에** — 9장 `ADR-01` · 4.1 `REQ-FUNC-004`

> ⚠️ **자주 하는 오해** — "유지" 결론을 **오류나 실패로 처리하면 안 된다.** SRS 6.1.3이 이걸 못 박았다: `gatingResult: KEEP_CURRENT`는 HTTP `200`으로 반환하고 `error` 키를 두지 않는다.

### 3.2 성적표에서 일부 사용자를 일부러 뺀다

**이상한 점** — 이 서비스의 성공 지표는 "조합안 선택률"인데, **"유지" 결론을 받은 사용자는 분모에서 뺀다.** 성적을 유리하게 만드는 것처럼 보인다.

**이유** — 빼지 않으면 이렇게 된다.

```
정직하게 "유지"를 권한다  →  선택할 조합안이 없다
                        →  선택률이 떨어진다
                        →  점수를 올리려면 정직함을 포기해야 한다
```

**잘하면 점수가 내려가는 지표는 지표가 아니다.** 그래서 뺀다.

**어디에** — 9장 `ADR-05` · 11.1 북극성 지표

> 대신 **제외군이 30%를 넘으면 산식을 다시 설계**한다는 안전장치를 걸어뒀다.

### 3.3 AI가 금액을 계산하지 않는다

**이상한 점** — AI를 쓰는데 정작 계산은 안 시킨다.

**이유** — AI는 같은 질문에 다른 답을 낼 수 있다. 그런데 이 서비스는 **같은 입력에 같은 금액이 나와야 한다**(재계산 불일치 0건). 그리고 *"AI가 혜택을 보장한다"* 는 오해는 규제 문제가 된다.

**AI가 하는 일은 딱 둘이다.**

| 하는 일 | 안 하는 일 |
| --- | --- |
| ⓐ 약관을 쉬운 말로 요약 | 혜택금액 계산 |
| ⓑ 계산 근거를 사람 말로 설명 | 최종 조합 추천 |

**어디에** — 9장 `ADR-02` · 3장 시스템 맥락(노란 테두리 = AI 진입 금지 영역)

### 3.4 해지를 대신 해주지 않는다

**이상한 점** — 계산까지 다 해놓고 정작 실행은 사용자가 직접 해야 한다.

**이유** — 마이데이터 사업자에게 **해지·전환을 대행할 권한이 없다.** 그래서 두 가지만 한다.

- 새 카드 → 카드사 페이지로 **이동 링크만**
- 해지 → *"카드사에서 직접 진행하셔야 합니다"* **안내만**

그리고 정직한 부분이 하나 더 있다. **30일 뒤에 "정말 바꾸셨어요?" 하고 한 번 물어보는데, 대답이 없으면 "안 바꿨다"로 센다.** 그런데도 재촉하지 않는다 — 자기 서비스의 약점을 일부러 계속 쳐다보려고 만든 장치다.

**어디에** — 9장 `ADR-04` · 4.1 `REQ-FUNC-009`·`010` · 11.2 Blind-spot 지표

### 4.1 4장이 왜 가장 중요한가

요구사항 27건이 **세 갈래**로 나뉜다. 이 구분을 모르면 4장이 안 읽힌다.

| 갈래 | 뜻 | 개수 |
| :---: | --- | :---: |
| `REQ-FUNC` | **해야 할 일** — 계산한다, 보여준다 | 12 |
| `REQ-NF` | **잘 지켜야 할 조건** — 5초 안에, 오류 0.1% 이하로 | 9 |
| `REQ-EXC` | **문제 생겼을 때** — 어떻게 거절하나 | 6 |

**`REQ-EXC` 6건이 특이하다.** 전부 *"결과를 내지 않는 것이 정답"* 인 경우다. 미래 지출을 안 적었으면 계산해주지 않고, 근거가 6개 미만이면 결과를 아예 안 보여준다.

<details>
<summary><b>답 확인 (펼치기)</b></summary>

1. **미래 지출을 기준으로** 계산한다. 다른 서비스는 과거 소비만 본다
2. **Gross Benefit − 전환비용 3항목**(연회비 변동·실적 재달성·전환 실행)
3. **`200`.** 오류가 아니라 정상 결과이므로 `error` 키를 두지 않는다
4. **6개.** 실적구간·통합할인한도·연회비·제외조건·기준일·미반영 항목
5. **ⓐ 약관 요약 ⓑ 추천 근거의 자연어 설명.** 금액 계산은 하지 않는다
6. **계산 요청 시 3개를 모두 미리** 계산한다. 탭 전환은 조회만 한다
7. **오조회(타인 데이터 노출).** 컴플라이언스가 단독으로 중단하고 신고한다
8. **계속한다.** 단 "최근 확인된 데이터 기준" 경고와 **기준일**을 반드시 표시한다
9. **안 보여준다.** 전체를 "부분"으로 처리하고 추천을 중단한다
10. **"예상대로" 결론이 "유지"인 사용자.** 선택할 조합안이 없는데 분모에 넣으면 정직할수록 점수가 떨어진다
11. 소수점을 쓰면 **배분 합계 오차 ≤ 1원**과 **재계산 불일치 0건**을 동시에 만족할 수 없다
12. **있었다.** 규칙 엔진의 계산 순서·전환비용 산정법(D16)이 미정이었고, 2026-08-25 `[계산 명세서] CardFit (한글).md`로 확정됐다

</details>

| 통합할인한도 | 한 달에 받을 수 있는 혜택의 상한 |
| 제외항목 | 혜택·실적에서 빠지는 업종·거래 |
| `rule_version` | 카드 약관의 **버전 번호** |
| Gross / Net Benefit | 총 혜택 / **비용 뺀** 실제 이득 |
| 게이팅 | 바꿀 가치가 없으면 "유지"를 답하는 판단 |
| 조합안 (PlanCandidate) | 해지·유지·신규추가로 짠 **카드 구성안** |
| 완주 | 결과대로 **실제로 해지·전환까지 끝낸 것** |
| 북극성 지표 | 이 제품의 **대표 성공 지표** 하나 |
| Guardrail | 넘으면 **서비스를 멈추는** 하한선 |
| Blind-spot 지표 | 개선도 중단도 안 하지만 **반드시 봐야 하는** 것 |
| p95 | 100번 중 95번은 이 시간 안에 끝난다 |
| SLO | 이 요구사항의 **합격 기준 숫자** |
| ADR | **왜 이렇게 설계했는지** 적어둔 기록 |
| TBD | 아직 안 정해짐 (**일부러 비운 것**) |
| `CF-4001` 같은 코드 | 거절 이유를 구분하는 **에러 번호** |

## 9. 읽다가 TBD를 만나면

SRS에는 `TBD`와 🔴가 여러 번 나왔다. **빠뜨린 게 아니라 일부러 비운 것**이었고, 무엇에 막혀 있는지가 함께 적혀 있었다. **2026-08-25에 대부분 채워졌다.**

**가장 컸던 미정 사항 3개가 어떻게 풀렸나**

| | 무엇이 안 정해졌었나 | 어떻게 풀렸나 |
| :---: | --- | --- |
| **D16** | 규칙 엔진의 **계산 순서와 전환비용 산정법** | `[계산 명세서] CardFit (한글).md` 2~4장에 RE-1~8을 확정했다 |
| **D2** | "얼마 이상 이득이면 바꾸라고 할지" **기준 숫자** | **월 3,000원 이상 그리고 지금보다 10% 이상** — 둘을 모두 넘어야 변경을 권한다 |
| **D11** | 마이데이터 연동을 지금 스택에서 할 수 있는지 | **미뤘다.** 사전 생성한 시연 데이터로 개발을 진행하고, 실제 연동 시점에 다시 판단한다 |

**D16 → D2 순서를 지켰다.** 전환비용을 어떻게 계산할지 모르는 채로 기준 숫자를 정하면 그 숫자가 무의미해지기 때문이다.

**아직 🟡로 남은 5건은 "없어진 것이 아니라 미뤄진 것"이다.** 시연 데이터가 외부 연결을 대신하고 있을 뿐이라, 실제 서비스로 갈 때 다시 열린다. 전체 목록과 상태는 SRS **10.3**에 있다.
