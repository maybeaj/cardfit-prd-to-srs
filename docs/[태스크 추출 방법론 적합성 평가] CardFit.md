**현재 태스크 리스트는 방법론의 4단계 중 2단계를 충족하고, 2단계가 미충족이다.**

| **2** | 로직 CQRS 분해 | **✕ 미충족** | Read/Write 분류 **0건**. 컴포넌트 단위로만 분해됨 |

**핵심 결론 3가지**

1. **FE 24건 중 18건(75%)이 BE에 직렬로 묶여 있다.** Mock 태스크가 없어 프론트가 백엔드 완성을 기다린다. 방법론 Step 1의 "추출 대상 3"이 정확히 이 문제를 겨냥한다.
2. **위상 계층이 13개다.** Mock을 도입하면 **10개로 줄어든다**(아래 2.3 시뮬레이션). 3개 계층만큼 직렬 구간이 짧아진다.
3. **`Blocks` 관계는 이미 계산 가능하다.** 문서에 표기만 없을 뿐, 선행 태스크 열에서 **65개 노드 · 151개 엣지**가 도출된다. 자동 생성으로 해소된다.

## 2. Step 1 — 계약·데이터 명세 : △ 부분 충족

### 2.1 추출 대상 1 (데이터베이스) — ✅ 충족

`DA-001`~`DA-012` 12건이 테이블 15개를 덮는다. 방법론의 예시(`[DB] User 및 Profile 테이블 스키마, 마이그레이션 스크립트 작성`)와 입도가 일치한다.

**다만 마이그레이션이 명시돼 있지 않다.** 현재 표현은 *"`users` — 동의 상태·범위·일시"* 로 스키마 정의만 가리킨다. Prisma 마이그레이션 스크립트 작성이 태스크에 포함되는지 불명확하다.

> **수정** — DA 태스크의 `Feature` 표현을 *"스키마 정의 + 마이그레이션 스크립트"* 로 명시한다. 태스크를 늘리지 않고 표현만 고친다.

### 2.2 추출 대상 2 (API 및 통신 계약) — ❌ 미충족

**`API Spec` 성격의 태스크가 0건이다.** 현재 `BE-033`~`BE-036`은 *구현* 태스크이지 *계약 정의* 태스크가 아니다.

| | 현재 | 방법론 요구 |
| --- | --- | --- |
| 태스크 | `BE-033 POST /api/v1/calculate` (구현) | `[API Spec] Calculation 도메인 Request/Response DTO 및 에러 코드 정의` |
| 시점 | BE-016 이후 | **구현보다 먼저** |
| 소비자 | 없음 | FE·Mock·테스트가 인용 |

이는 SRS의 공백에서 비롯된다. **SRS 6.1은 엔드포인트 7행 목록만 있고 요청·응답 스키마와 에러 코드가 없다.** 그래서 계약 태스크를 만들 재료가 문서에 없었다.

> **수정** — `CT-001`~`CT-004` 신설(2.4 참조). 이것이 **W0 선행 정비**의 실체다.

### 2.3 추출 대상 3 (Mock 데이터) — ❌ 미충족

**Mock 태스크가 0건이고, 그 결과가 수치로 드러난다.**

```
FE 태스크 24건 중 BE 선행에 묶인 것 : 18건 (75%)
위상 계층                          : 13개
  L9  ~ L12 구간이 FE 15건으로 꼬리를 이룬다
```

**Mock 도입 시뮬레이션** — FE의 BE 의존을 Mock 의존으로 치환하면:

| | 위상 계층 |
| --- | :---: |
| 현재 | **13개** |
| Mock 도입 후 | **10개** |

3개 계층이 줄어든다. 방법론이 *"프론트엔드 에이전트가 백엔드 완성을 기다리지 않도록"* 이라고 명시한 목적이 정확히 이 수치다.

> **수정** — `MK-001`~`MK-004` 신설. FE 태스크의 선행을 `BE-xxx` → `MK-xxx`로 교체하고, BE는 통합 시점에만 의존시킨다.

### 2.4 Step 1 신규 태스크 8건

| 신규 ID | 유형 | Feature | 선행 | 근거 |
| :---: | :---: | --- | :---: | :---: |
| **CT-001** | API Spec | Calculation 도메인 DTO·에러 코드 정의 (`/calculate`, `/calculations/{id}`) | None | SRS 6.1 · 4.3 |
| **CT-002** | API Spec | Evidence 도메인 DTO·에러 코드 정의 (근거 6항목 스키마) | CT-001 | SRS 4.1 REQ-FUNC-006 |

| **CT-004** | API Spec | 공통 에러 코드 체계 정의 (400·거부·부분·만료) | CT-001 | SRS 4.3 REQ-EXC-001~006 |
| **MK-001** | Mock | 계산 결과 Mock — 3시나리오 · 유지/변경 두 결론 | CT-001 | SRS 4.1.1 |

**`MK-003`이 6종을 모두 담아야 하는 이유** — 예외 화면(`FE-018`~`FE-020`)이 전부 BE 예외 구현을 기다리게 된다. SRS 4.3의 6건은 *"결과를 내지 않는 것이 정답"* 인 경로라, 실제로 그 응답을 만들어 보지 않으면 화면을 설계할 수 없다.

## 3. Step 2 — 로직 CQRS 분해 : ✕ 미충족

### 3.1 현재 분해 축이 다르다

현재 BE 39건은 **컴포넌트 축**으로 분해돼 있다(`RuleEngine`, `EvidenceAssembler`, `OutcomeTracker`). 방법론은 **조회(Read)와 변경(Write)** 축을 요구한다.

| | 현재 | 방법론 |
| --- | --- | --- |
| 분해 축 | 컴포넌트·클래스 | Query / Command |
| 위험도 표현 | 복잡도 H/M/L | 상태 변경 여부 |
| 예시 | `BE-021 EvidenceAssembler` | `[Feature/Query] 계산 근거 조회 로직 구현` |

**축이 다르다고 해서 현재 분해가 틀린 것은 아니다.** 컴포넌트 분해는 SDD 클래스 다이어그램과 1:1로 이어져 구현 지시가 명확하다. 다만 **상태를 바꾸는 태스크와 읽기만 하는 태스크가 구분되지 않아**, 리뷰 강도와 롤백 위험이 같아 보인다.

### 3.2 두 축을 함께 쓰는 방식을 권한다

컴포넌트 분해를 유지하되 **`Q`/`C` 라벨을 추가**한다. 재분해하지 않는다.

| 라벨 | 뜻 | 리뷰·배포 함의 |
| :---: | --- | --- |
| `cqrs:query` | 상태를 바꾸지 않음 | 롤백 불필요. 리뷰 부담 낮음 |
| `cqrs:command` | 상태를 바꿈 | 마이그레이션·롤백 계획 필요 |
| `cqrs:mixed` | 두 성격이 섞임 | **분해 검토 대상** |

### 3.3 실제 분해가 필요한 3건

| 태스크 | 섞인 성격 | 분해안 |
| :---: | --- | --- |
| **BE-027** `OutcomeTracker` | 선택 기록(Write) + 완주 집계(Read) | `BE-027a` 선택 기록·발송(Command) / `BE-027b` 완주율 집계(Query) |
| **BE-032** `RuleDataPipeline` | 약관 수집(Write) + 최신성 판정(Read) | `BE-032a` 수집·rule_version 발행(Command) / `BE-032b` 최신성 점검·제외 판정(Query) |
| **BE-021** `EvidenceAssembler` | 근거 조립(Read) + **6항목 미달 거부**(정책 판정) | `BE-021a` 근거 조립(Query) / `BE-021b` 6항목 게이트(Policy) |

**BE-021의 분해가 특히 유효하다.** 미달 거부는 GR3에 직결된 P0 판정이라, 조회 로직과 섞여 있으면 **테스트 실패 시 원인이 조회인지 판정인지 구분되지 않는다.**

> **수정** — 3건 분해로 BE 39건 → **42건**. 나머지 36건은 라벨만 추가한다.

## 4. Step 3 — AC → 테스트 태스크 : △ 부분 충족

### 4.1 재료는 이미 충분하다

방법론이 요구하는 GWT 형식 인수 조건이 **STD에 27건 완비돼 있다.** 이 항목은 대부분의 프로젝트가 비어 있는 지점인데, CardFit은 사전조건·절차·기대 결과·판정 SLO까지 갖췄다. **변환할 재료가 있다는 점이 강점이다.**

### 4.2 입도가 부족하다

| | 현재 | 방법론 요구 |
| --- | --- | --- |
| 태스크 수 | **3건** (`QA-001`~`003`) | Feature당 1건 |
| 커버 범위 | 1건이 TC 9~12건을 묶음 (**1:9**) | 1:1 |
| 문제 | *"기능 테스트 12건 구현"* 이 완료됐는지 부분 판정 불가 | 개별 완료 추적 가능 |

**QA-001 하나가 TC-FUNC-001~012를 통째로 담고 있어**, 12건 중 8건만 통과한 상태를 이슈로 표현할 수 없다.

### 4.3 수정 — 요구사항 단위로 27건 분해

`QA-001`~`003`(3건) → `TS-001`~`TS-027`(27건). 요구사항 27건과 1:1이고, STD의 TC 27건과도 1:1이다.

```
REQ-FUNC-004 ─── TC-FUNC-004 ─── TS-004 [Test] 게이팅 GWT 시나리오 테스트 코드 작성
                                    │
                                    └─> BE-017 이슈의 DoD 체크리스트로 삽입
```

**방법론 Tip의 반영** — 추출된 AC 내용은 Step 2 Feature 이슈의 DoD에 삽입된다. `TPL-CARDFIT-001` 2.4의 공통 DoD 두 번째 항목(*"대응 테스트 케이스(STD)가 구현되고 통과하는가?"*)이 이 연결이며, 구체 TC ID를 채워 넣는다.

**`QA-004`~`007`(게이트·보안·부하)은 유지한다.** 이들은 특정 기능이 아니라 시스템 전체를 대상으로 하므로 Feature 1:1 대응이 성립하지 않는다.

## 5. Step 4 — NFR 추출 및 의존성 매핑 : △ 부분 충족

### 5.1 NFR 태스크는 존재하나 흩어져 있다

방법론의 예시(`[Infra] k6 부하 테스트 스크립트 작성`, `[Sec] 암호화·로깅 마스킹 파이프라인 구축`)에 대응하는 태스크가 `IN`과 `BE`, `DA`에 나뉘어 있다.

| NFR | 대응 태스크 | 현재 접두어 |
| :---: | --- | :---: |
| REQ-NF-001 성능 | IN-010 · BE-037 · QA-007 | IN·BE·QA |
| REQ-NF-002 정확성 | BE-020 · IN-005 | BE·IN |
| REQ-NF-004 보안 | DA-011 · BE-002 · QA-006 | DA·BE·QA |
| REQ-NF-005 비용 | BE-006 | BE |
| REQ-NF-006 감사 | DA-010 · BE-028 | DA·BE |
| REQ-NF-009 계측 | IN-013 · BE-029 | IN·BE |

**흩어진 것 자체는 문제가 아니다** — 계층별 구현이 실제로 나뉘기 때문이다. 다만 *"REQ-NF-004를 만족시키는 태스크가 다 발급됐는가"* 를 한눈에 볼 수 없다.

> **수정** — 태스크를 옮기지 않고 **`nfr:` 라벨을 추가**한다(`nfr:req-nf-004`). GitHub Project에서 라벨 필터로 NFR별 묶음이 보인다.

### 5.2 `Blocks` 역방향이 표기돼 있지 않다 — 템플릿 필수 필드

템플릿의 `## 🚧 Dependencies & Blockers`는 **양방향**을 요구한다.

```markdown
- Depends on: #12 (DB 인프라 세팅 이슈)
- Blocks: #24 (로그인 기능 구현 이슈)
```

현재 태스크 리스트는 `선행 태스크` 열만 있어 `Depends on`만 채울 수 있다.

**그러나 이미 계산 가능하다.** 선행 관계를 뒤집으면 **65개 노드 · 151개 엣지**가 나온다.

**가장 많은 태스크를 막고 있는 8건**

| 태스크 | 차단 수 | Feature |
| :---: | :---: | --- |
| IN-004 | **9건** | Vercel 배포 연결 |
| DA-001 | 7건 | `users` 스키마 |
| DA-005 | 7건 | `benefit_rules` 스키마 |
| DS-001 | 6건 | 디자인 토큰·컴포넌트 |
| IN-001 | 5건 | Next.js 초기화 |
| BE-016 | 5건 | `CalculationOrchestrator` |
| DA-006 | 5건 | `calculations` 스키마 |
| BE-012 | 5건 | `RuleEngine` 계산 코어 |

**이 표가 착수 우선순위의 근거다.** IN-004·DA-001·DA-005 세 건이 23개 태스크를 막고 있어, 지연되면 파급이 가장 크다.

> **수정** — `tools/` 에 `Blocks` 자동 생성 스크립트를 추가하고, 태스크 리스트에 `후행 태스크` 열을 넣는다. **수동 관리하지 않는다** — 선행 열이 바뀌면 자동으로 따라와야 어긋나지 않는다.

### 7.3 순서에 대한 근거 3가지

**① 왜 4번(인프라 기반)이 Step 1 뒤에 오는가**

방법론은 인프라를 Step 4로 둔다. 그러나 `IN-001`(Next.js 초기화)·`IN-003`(Prisma 환경)은 **DA 태스크의 실행 전제**다. 문서 *작성* 순서는 Step 1이 먼저지만, 실제 *착수* 순서는 인프라가 먼저다.

**분리해서 처리한다** — Step 1의 계약 문서를 먼저 쓰되, 인프라 기반 6건을 4번에 넣어 **착수 시점에는 인프라가 앞서도록** 한다. Step 4의 NFR 인프라(게이트·관측·알림)는 10번에 그대로 둔다.

**② 왜 8번(FE 24건)이 앞당겨졌는가**

Mock(3번)이 먼저 나오므로 FE는 BE 완성을 기다리지 않는다. 2.3 시뮬레이션의 **위상 계층 13 → 10** 효과가 여기서 실현된다. 이전 순서안(W8)에서 FE가 늦었던 이유가 Mock 부재였다.

**③ 왜 12번(계산 도메인)이 마지막인가**

`BE-011`~`BE-020` 10건이 **D16(규칙 엔진 계산 명세)** 에 막혀 있다. 지금 쓰면 AC가 *"`{RE-1 확정 후}` 순서로 계산한다"* 로 남고, D16 확정 후 10건을 전부 다시 손봐야 한다. **확정 후 한 번에 쓰는 편이 총량이 적다.**

### 7.4 선행 조건 — 제작 전에 해소해야 할 것

| # | 선행 | 막는 배치 | 성격 |
| :---: | --- | :---: | --- |
| 1 | **SRS 6.1에 요청·응답 스키마 추가** | 1번 (CT) | SRS 보강 — 현재 엔드포인트 목록만 있음 |
| 2 | **에러 코드 체계 확정** | 1번 (CT-004) | SRS 4.3의 6개 예외에 코드 부여 |
| 3 | **D16 규칙 엔진 계산 명세** | 12번 | **기획 결정** |
| 4 | **D2 · D5** | 12번 | 기획 결정 (D16 선행) |
| 5 | **D14 도구 선정** (APM·알림·발송·분석) | 10번 | 기술 선택 |

## 8. 이 평가의 한계

1. **CQRS 분해 3건은 제 판단이다.** `BE-021`을 조회와 정책 판정으로 나누는 것이 실제 구현에서 과분해일 수 있다. 팀이 한 클래스로 구현할 예정이면 라벨만 `cqrs:mixed`로 두는 편이 낫다.
2. **테스트 태스크 27건은 요구사항 단위 가정이다.** 컴포넌트 단위로 더 잘게 나누면 늘고, 도메인 단위로 묶으면 준다. STD의 TC 27건과 1:1이라는 점을 근거로 삼았다.
3. **Mock 태스크 4건의 입도는 도메인 기준이다.** 화면 단위로 나누면 더 늘어난다.
4. **위상 계층 13 → 10 시뮬레이션은 FE의 BE 의존을 전건 Mock으로 치환한 값이다.** 실제로는 통합 시점에 BE 의존이 남으므로, 개발 완료 시점이 아니라 **착수 가능 시점**의 개선으로 읽어야 한다.
