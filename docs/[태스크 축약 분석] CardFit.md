## 1. 분석 방법

142건을 파싱해 의존성 그래프를 만들고, **병합했을 때 무엇을 잃는가**를 세 기준으로 측정했다.

| 기준 | 측정 방법 |
| --- | --- |
| **차단 전파** | 비차단 태스크가 차단 그룹에 흡수되면 안 막혔던 것이 막힌다 |
| **전이 차단** | 선행이 막혀 이미 사실상 막혀 있던 것은 흡수해도 손해가 아니다 |
| **위상 계층** | 병합이 의존 사슬을 길게 만들면 병렬성이 준다 |

**전이 차단 계산이 판정을 뒤집었다** — 직접 차단은 11건이지만 **전이 포함 28건**이다. 즉 `BE-006`·`BE-007`·`BE-038`·`BE-032b`는 병합 여부와 무관하게 이미 막혀 있어, 차단 그룹에 넣어도 잃는 것이 없다.

## 4. 하지 말아야 할 병합 3건

무리한 병합이 무엇인지 먼저 특정했다. 아래 셋은 **묶으면 잃는 것이 생긴다.**

### 4.1 `BE-023`(약관 요약)을 차단 그룹에 넣지 않는다 ← 실측으로 발견

첫 설계에서 `BE-023`·`BE-024`·`BE-032a`·`BE-032b`를 "약관·AI"로 묶었더니 **비차단인 `BE-023`이 차단 그룹에 흡수됐다.**

| | 상태 | 근거 |
| :---: | :---: | --- |
| BE-023 약관 요약 | **비차단** | **DEC-3a — 약관은 공개 문서라 개인정보가 없다.** 즉시 진행 가능 |
| BE-024 근거 설명 | 🔴 차단 | DEC-3b — 사용자 금융정보 국외 이전 검토 필요 |

**AI 기능 중 유일하게 지금 시작할 수 있는 것을 막게 된다.** 분리해서 `BE-14`를 단독 그룹으로 두었고, 그 결과 **차단 전파 손해가 0건**이 됐다.

### 4.2 `BE-021b`(근거 게이트)를 `BE-021a`와 다시 합치지 않는다

Phase 0에서 분리한 이유가 그대로 유효하다. 미달 거부는 **GR3 직결 P0 판정**이라, 조회 로직과 섞이면 **테스트 실패 시 원인이 조회인지 판정인지 구분되지 않는다.**

### 4.3 `CT-004`(에러 코드)를 DTO와 합치지 않는다

`CF-4221`(GR3)과 `CF-4030`(GR5)을 싣는 통로다. **Guardrail 2건에 직결된 P0**이므로 DTO 정의와 우선순위가 다르다.

## 5. 감수해야 할 것 3가지

### 5.1 위상 계층이 10 → 11로 **1 늘어난다**

병합이 그룹 간 의존을 직렬화하기 때문이다. 예컨대 `FE-03`이 8개 화면을 담으면, 그중 하나만 준비돼도 시작할 수 있던 것이 그룹 전체를 기다리게 된다.

**영향은 제한적이다** — 늘어난 계층은 1개이고, 대신 관리 대상이 142 → 53으로 준다. 다만 *"태스크를 줄이면 병렬성이 좋아진다"* 는 직관은 사실이 아님을 밝혀 둔다.

### 5.2 진행률의 해상도가 낮아진다

`TS-01`(기능 테스트 12건)이 한 태스크가 되면 **12건 중 8건 통과 상태를 이슈로 표현할 수 없다.** Phase 0에서 27건으로 나눈 이유가 바로 이것이었다.

**완화책** — 병합 태스크의 `Task Breakdown` 체크리스트에 원래 태스크를 한 줄씩 남긴다. 이슈는 1장이지만 체크박스가 12개다.

### 5.3 큰 그룹 2건은 한 사람이 맡기 어렵다

| 그룹 | 크기 | 성격 |
| :---: | :---: | --- |
| TS-01 | 12건 | 기능 테스트 전체 |
| FE-03 | 8건 | 결과 화면 전체 |

**분담이 필요하면 이 둘만 다시 쪼개면 된다.** 그 경우 53 → 55~57건이 되며, 여전히 목표 범위다.

## 6. 가장 큰 결정 — TS 27 → 3

**축약분 89건 중 24건이 여기서 나온다.** 그런데 이건 Phase 0에서 방법론에 맞추려고 3 → 27로 늘렸던 것을 되돌리는 것이다.

### 6.1 방법론과의 관계

방법론 Step 3은 두 가지를 함께 말한다.

| 방법론 문장 | 함의 |
| --- | --- |
| *"AC를 테스트 코드 작성 Task로 변환하여 추출"* | 테스트를 **태스크로** 만들라 |
| *"추출된 AC 내용들은 Feature 이슈의 DoD 체크리스트 항목으로 바로 삽입"* (Tip) | AC는 **Feature의 DoD로** 들어간다 |

**Tip이 축약의 근거가 된다.** AC의 판정 책임이 Feature 태스크 DoD에 있다면, 테스트 태스크는 *"코드를 작성하는 작업 단위"* 로만 남으면 되고 요구사항 1:1일 필요가 없다.

### 6.2 세 가지 선택지

| 안 | TS 건수 | 총계 | 잃는 것 |
| :---: | :---: | :---: | --- |
| **A. 3건 묶음** (권장) | 3 | **53** | 진행률 해상도. Breakdown 체크박스로 완화 |
| B. 도메인 6건 | 6 | 56 | 상동, 완화 폭 큼 |
| C. 27건 유지 | 27 | 77 | **목표 미달** — 50 내외에 못 간다 |

**C를 택하면 축약 목표 자체가 성립하지 않는다.** 다른 접두어를 아무리 줄여도 77건이 하한이다.

## 8. 이 분석의 한계

1. **병합 맵은 도메인 판단이다.** 그래프 무결성(커버리지·차단·순환)은 기계로 검증했지만, *"이 셋을 한 사람이 맡을 만한가"* 는 팀 구성에 달렸다.
2. **복잡도 재산정을 하지 않았다.** `FE-03`은 8건을 묶었으므로 원래 `M`들의 합이지만, 새 등급을 부여하지 않았다. 실행 시 재산정이 필요하다.
3. **53건은 하나의 해다.** TS 선택지 B를 고르면 56건, 큰 그룹 2건을 쪼개면 57건까지 늘어난다. 모두 "50 내외"의 범위로 본다.
4. **위상 계층 11은 그룹 단위 계산이다.** 그룹 안의 순서는 `Task Breakdown` 체크리스트가 담당하므로, 실제 작업 순서가 늘어난 것은 아니다.
