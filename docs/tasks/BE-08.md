## ✅ Task Breakdown (실행 계획)
- [ ] **보유카드 사전 컷** — 최근 3개월 사용액 상위 8장. 컷으로 빠진 카드는 근거 화면에 목록으로 표기(CALC §4.1)
- [ ] **부분집합 생성** — 빈 조합 제외. 카드 8장 기준 최대 256개
- [ ] **신규 후보 풀 3장** — 제약 필터 통과 + 지출 상위 3개 카테고리 적합도 점수 상위 3장. 이미 보유한 상품은 제외(RE-7)
- [ ] **조합당 신규 최대 1장** — 동시에 두 장을 새로 발급하라는 제안은 하지 않는다
- [ ] **제약 필터** — 최대 카드 수 · 연회비 상한 · 신규 발급 허용 여부
- [ ] **최종 후보 상한 20개** — `ΔNet` 내림차순 정렬 후 절단
- [ ] **정렬 전순서 5키** — `ΔNet` → 전환비용 → 카드 수 → 연회비 합 → `card_product_id` 사전순(CALC §4.3)
- [ ] **배분 구현** — RE-8 택일. 카테고리 금액을 한 카드에만 배정
- [ ] **합계 정합 검증** — `AllocationService.verifySumWithin1Won()`. 잔여 오차는 배분 금액 최대 카테고리에 흡수
- [ ] **단계적 전환 제안** — 변경 항목을 효과 크기 내림차순으로. **실행 대행 동작을 만들지 않는다**(REQ-FUNC-011)
- [ ] 성능 측정 — 카드 3·5·10장 케이스의 후보 수와 소요시간 기록(QA-03 입력)

## 🧪 Acceptance Criteria (BDD/GWT)

**Scenario 1: 후보가 상한 안에서 생성된다**
- Given: 보유 카드 10장인 사용자가 주어지고
- When: 조합 후보를 생성하면
- Then: 사전 컷 8장이 적용되고 최종 후보가 20개 이하이며 `p95 ≤ 5s` 를 만족한다(CALC §4.1 · REQ-NF-001).

**Scenario 2: 배분 합계가 입력 총액과 일치한다**
- Given: 3으로 나누어떨어지지 않는 금액이 포함된 입력이 주어지고
- When: 배분을 수행하면
- Then: 카드별 배분액 합계와 입력 총액의 차이가 1원 이하다(REQ-FUNC-005 · TC-FUNC-005).

**Scenario 3 (실패 흐름): 같은 입력이 다른 후보 순서를 내지 않는다**
- Given: 동일 입력으로
- When: 후보 생성을 10회 반복하면
- Then: 후보 목록과 순서가 모두 같다. 정렬이 전순서가 아니면 재계산 불일치가 발생한다(CALC §4.3 · REQ-NF-002).

**Scenario 4 (실패 흐름): 신규 발급이 조합당 2장 이상 제안되지 않는다**
- Given: 신규 발급이 허용된 제약이 주어지고
- When: 생성된 후보를 검사하면
- Then: 신규 카드가 2장 이상 포함된 조합이 0건이다.

## ⚙️ Technical & Non-Functional Constraints
- 성능: **REQ-NF-001** `POST /calculate` p95 ≤ 5s · 서버리스 하드 타임아웃 0건. 후보 상한이 이 목표의 수단이다
- 정확성: **REQ-FUNC-005** 배분 합계 오차 ≤ 1원. DB가 지켜주지 않으므로 애플리케이션이 검증한다(SDD §4.2)
- 범위: **REQ-FUNC-011**(Could) 단계적 전환은 **제시 방식이지 실행 지원이 아니다**
- 한계: 후보 상한 20개는 성능 근거이지 최적성 보장이 아니다. 21번째 후보가 더 나을 가능성을 배제하지 못한다(CALC §9장)
