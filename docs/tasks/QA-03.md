## 🧪 Acceptance Criteria (BDD/GWT)

**Scenario 1: 계산이 5초 안에 끝난다**
- Given: 카드 10장 케이스로
- When: `POST /calculate` 에 부하를 인가하면
- Then: p95 ≤ 5s이고 하드 타임아웃이 0건이다(REQ-NF-001).

**Scenario 2: 근거 조회가 1초 안에 끝난다**
- Given: 동일 조건에서
- When: `GET .../evidence` 에 부하를 인가하면
- Then: p95 ≤ 1s다.

**Scenario 3 (실패 흐름): 카드 장수에 따라 폭발하지 않는다**
- Given: 카드 3·5·10장 케이스를 순차 측정하고
- When: 소요 곡선을 비교하면
- Then: 후보 수가 사전 컷과 상한 20개로 억제돼 지수적으로 늘지 않는다(CALC §4.1).

**Scenario 4 (실패 흐름): 타임아웃이 발생하면 대응안을 결정한다**
- Given: 하드 타임아웃이 1건이라도 관측되면
- When: 대응안을 검토하면
- Then: ⓐ 또는 ⓑ 중 하나를 선택하고, **어느 쪽이든 탭 전환 재계산 없음(ADR-03)은 유지**한다.

## ⚙️ Technical & Non-Functional Constraints
- 성능: **REQ-NF-001** 계산 p95 ≤ 5s · 근거 p95 ≤ 1s · 결론 도달 p95 ≤ 5분 · 타임아웃 0건
- 기술 제약: 서버리스 실행 상한은 `p95` 와 **별개인 하드 타임아웃**이다(§1.5.1 신규 제약 ②)
- 측정: `latency_samples`(`IN-06`)가 관측 창구다. 별도 APM 도구를 도입하지 않는다
- 한계: 픽스처 부하 특성은 실제와 다르다(FXT §9장 한계 6)
