## 🧪 Acceptance Criteria (BDD/GWT)

**Scenario 1: 제안값으로 입력 강제가 사라진다**
- Given: 과거 3개월 소비가 적재된 사용자가 주어지고
- When: 온보딩 초기값을 요청하면
- Then: 카테고리별 제안값이 반환되고, 사용자가 아무것도 입력하지 않아도 계산이 가능하다(REQ-FUNC-007).

**Scenario 2: 같은 스냅샷은 같은 제안을 낸다**
- Given: 동일한 과거 스냅샷이 주어지고
- When: 제안을 10회 반복 산출하면
- Then: 결과가 모두 같다. 제안이 흔들리면 재계산 불일치의 원인이 된다(REQ-NF-002).

**Scenario 3 (실패 흐름): 데이터가 부족해도 실패하지 않는다**
- Given: 과거 소비가 1개월치만 있는 사용자가 주어지고
- When: 제안을 요청하면
- Then: 있는 기간으로 제안하되 근거 기간을 함께 반환한다. 빈 응답이나 오류로 떨어지지 않는다.

**Scenario 4: 수정 여부가 기록된다**
- Given: 제안값이 생성된 상태에서
- When: 사용자가 한 항목을 수정하면
- Then: `was_edited` 가 기록된다. 수정률을 관측할 수 없으면 T3(완료율만 오르고 틀린 값이 통과)를 확인할 수 없다.

## ⚙️ Technical & Non-Functional Constraints
- 사용성: **REQ-NF-008** 온보딩 완료율 ≥ 60% · A군 대비 +15%p · 직접 입력 강제 0개
- 정확성: **REQ-NF-002** 결정론. 제안 산출에 무작위·현재 시각을 쓰지 않는다
- 트레이드오프: **T3** — 완료율만 오르고 수정률이 비정상이면 통과로 보지 않는다(TC-FUNC-007 비고)
- 데이터: 스냅샷 기준으로 읽는다. 갱신되는 소비 데이터를 참조하면 과거 계산 재현이 깨진다(A-002)
